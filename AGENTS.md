# AGENTS.md

This is the canonical repo instruction file for agents. Keep user-facing setup and CLI docs in `README.md`; `CLAUDE.md` is only a Claude Code compatibility pointer.

## Principles
- **No fallbacks. Fail fast and hard.** When something required is missing or fails — a dependency, an external tool, a file, an env var, a capability, an unexpected value — surface it immediately with a clear error or let the exception propagate. Never swallow it with a `try/except`-to-default, never silently degrade to an alternate path, never guess a default to keep going. This applies to everything, with no exceptions for any one dependency. (A multi-location lookup that a feature documents as part of its contract — e.g. resolving state files from a primary then a legacy location — is designed behavior, not an error-masking fallback.)
- **Diagnostics-only writes (journal, metrics) that fail after a run is already underway log a warning with the path and exception and continue; they follow the history-write precedent (`norn/runner.py:836-838`) because a diagnostics file must not kill a multi-dollar run at stage 60. This is the only permitted warn-and-continue path; serialisation is total (`_json_default`) so the failure can only be I/O.**

## Commands
- Install exactly like CI: `uv sync --group dev`.
- Run the CI-equivalent unit suite: `uv run python -m pytest tests/ -v`.
- Run a focused test: `uv run python -m pytest tests/test_runner.py::test_loop_retries -v`.
- There is no configured lint, formatter, or typecheck step in `pyproject.toml` or CI; do not invent one as required verification.
- Run a bundled pipeline: `uv run python -m norn run hello_v1`; list and inspect them with `uv run python -m norn list` and `uv run python -m norn describe hello_v1`.
- `uv run python -m norn models` prints every label with its pinned model, effort and `since` date, and the file path.
- Run an external config: `uv run python -m norn run examples/derived.py`; `bin/norn examples/derived.py` only auto-prepends `run` when the first arg is a file.
- The package is installed editable, so edits to `norn/pipelines/*.py` take effect on the next run; never reinstall or `uv sync` just to pick up a pipeline change.
- To drive a pipeline against another repo, `cd` there first: pipelines that pin `PROJECT_DIR = os.getcwd()` read it at import time, and `--project <norn checkout>` selects the environment without changing cwd.
- `bin/show_ci_data.py` dumps exactly what `check_and_fix_ci_v1` would feed Claude for a GitHub Actions run URL; it is a debug tool, not a pipeline.
- Run BATS only when needed: `bats -r bats/ -v`. CI does not run BATS, BATS expects bats-support/assert/file libraries, and several E2E tests call Claude.

## CLI State And Args
- `--resume` is checkpoint-based: it loads `<config>.checkpoint`, restores outputs, and skips completed stages as cached.
- `--continue` only resumes the agent session from the checkpoint; it reruns stages.
- Runtime state is `<config>.checkpoint` and `<config>.history`, not `.session`; these files are gitignored.
- **norn's own run state must never enter the target repository.** `<key>.checkpoint`, `<key>.history` and `<key>.runs/<n>/` are written into the launch directory for the whole run, so a run launched from inside the target repo puts them in that worktree. Two layers keep them out, and both live in `norn/state.py`: (1) every entry point calls `publish_state_key` **before importing the pipeline** — `norn run` (`norn/cli.py`) and the TUI's single import site `load_pipeline_with_args` (`norn/tui/launch.py`); a child run is a `norn run` subprocess and inherits the first. Pipelines read `NORN_STATE_KEY` at import time to build their snapshot-diff ignore flags, so publishing it after the import is useless. (2) `run_pipeline` calls `prepare_state_isolation` for every run that has a state key: it repairs a missing/stale `NORN_STATE_KEY` with a warning, refuses to start (`StateTrackedError`) when git already **tracks** norn's state — ignore rules never apply to tracked files, so the run is guaranteed to fail a commit gate later — and registers the paths in `.git/info/exclude`, which makes every git-based gate in every pipeline blind to them without the pipeline cooperating. Add new entry points to layer 1; never write to the repo's own `.gitignore` (that is itself a working-tree change).
- External pipeline files outside the workspace write new state beside a same-named file in the current working directory, with the external path only used as a read fallback.
- Positional args after the config are joined into `{param.args}`; `--arg KEY=VALUE` becomes `{param.KEY}`; `--skip` must match the exact human stage name, including spaces.
- Every key in `metadata["args"]` is rendered as a required positional by `norn describe` (`norn/cli.py:293-302`) and prompted for by the TUI launcher (`norn/tui/launch.py:33-46`); optional `--arg` knobs belong in the module docstring instead.
- `--arg model=`, `review_model=`, `aggregate_model=` and `codex_label=` are validated against `norn/model_labels.toml` at import; an unknown label fails the load, not the stage.

## Architecture
- `norn/` is the generic core and must not import from `norn.contrib`; contrib/domain code can import core.
- Real entrypoints are `norn/cli.py` for argument resolution, `norn/runner.py` for execution, `norn/dsl.py` for pipeline definitions, and `norn/stages/base.py` for stage contracts.
- External pipeline files are loaded with `importlib` and must define `config = Pipeline(...)`.
- Bundled pipelines live in `norn/pipelines/`; `norn/catalog.py` discovers their docstring and `metadata` via AST before importing, and they are run by name (`norn run implement_features_v1`).
- Every pipeline has exactly ONE home. Do not copy a bundled pipeline to another directory to run it by path — that duplication drifted for months before it was consolidated. Add new pipelines to `norn/pipelines/`; `examples/` holds only sample configs that demonstrate the run-by-path form.
- `implement_features_v1`'s commit stage tolerates auto-fixing pre-commit hooks: it clears any partial staging before committing, and if the commit is still rejected it re-stages what the hooks rewrote and retries **once** before failing. The re-stage list comes from git state via `_snapshot_diff.py --hook-fixes`, not from the step's `.changed` list, because hooks act on the whole staged set — the rewritten file is often one an earlier step staged.
- `implement_features_v2` is a deliberate parallel implementation of `implement_features_v1`, built from `tmp/implement-features-pipeline-improvements.md`. Intent: replace v1 once v2 has enough completed runs in its own history file to compare; until then both ship and v1 is frozen. Two things v2 changes that a reader will trip over: (1) every loop gate is repeated as a hard top-level stage with `on_failure=fail` (the in-loop check is a prompt, not a contract); a validation gate reruns its command only when the loop's last run left no proof for the current tree (`_proven_validation`: a content snapshot taken after a passing run, keyed by a hash of the command), because a blind rerun doubled the suite time and once killed a run on a flaky test that had just passed; the `preflight repository` clean-worktree check lists instead of rejecting modified files when the checkpoint shows a resume that stopped inside a baseline phase (`_BASELINE_PHASES`: a step, the aggregate, a review fix round), because that phase's own work is in the tree and hand-committing it moves HEAD and fails the step's HEAD guard, and (2) after all steps and aggregate validation, the review phase is a gate that writes `<feature_dir>/review.md` with a three-line header (`VERDICT: PASS`/`NEEDS_FIXES`, `Base: <sha>`, `Head: <sha>`) that the pipeline checks in shell; a stale or malformed header fails the gate. The rounds are asymmetric on purpose (`tmp/review-loop-plan.md`, from the 2026-09-17 transaction-tracker run where review was 43% of the spend and still ended NEEDS_FIXES): round 1 reviews the whole base..HEAD range, while rounds 2 and 3 re-check the previous round's blocking findings (archived to `review-<n>.previous.md` before the round deletes `review.md`, and read back by a `read previous review <n>` stage) and review the fix commits, because an unbounded re-review always finds one more nit and never reaches PASS. `VERDICT: PASS` needs no critical or major finding, not a clean sheet — minor findings and nits ride to the handoff. Work outside the run's own commits goes under `## For the human`: the fix agent has no git verbs, so it can never commit a file no step touched. The review prompt names the step files instead of inlining them; `all_step_names` (not the old `all_steps_summary`) is what it carries.
- v2's residual limits (deliberate deferrals to norn core, not oversights): commits are not transactional (a concurrent external write during a step is not detected); review is constrained and postcondition-checked, not sandboxed; hook-rewrite revalidation runs after the commit so a failure leaves already-committed rewritten code; resume matches commit subjects `refactor: <step stem>` and two plans sharing a step stem collide; turn caps (`max_turns`) are Claude-Code-only and v2 is not OpenCode-verified.
- Modules under `norn/pipelines/` whose name starts with `_` are private helpers (e.g. `_snapshot_diff.py`), not pipelines; `norn/catalog.py` skips them so they never appear in `norn list` or the TUI launcher.
- `norn/pipelines/_step_snapshot.py` is a private helper for `implement_features_v2`: content-aware worktree snapshots (SHA-1 digest per file to catch dirty-byte regressions), snapshot diff, and hook-fix detection; it produces NUL-separated path lists. `_snapshot_diff.py` is the v1 equivalent and stays untouched.
- `diff --root <toplevel>` filters the changed set through `unstageable_paths`, dropping the paths `git add -A --` would refuse: ones that became gitignored during the step (norn's own `*.checkpoint`/`*.runs` state files landing in the target repo's ignore list is the common case) and ones the step deleted that git never tracked. One refused pathspec aborts the whole `git add`, so without the filter a single such path kills the commit stage and the run. Dropped paths are listed on stderr — never silently. Tracked files are always kept, matching `git add`, which stages them regardless of ignore patterns. v2's final audit passes `--root` to the same diff, so a path that became gitignored during the run is dropped there too — it can never be committed, and reporting it as "changed without being committed" would fail an otherwise clean run with no move left to make. `_snapshot_diff.py` (v1) carries the same `--root` filter — the one deliberate exception to v1 being frozen, since the bug takes down a run. The probe code is duplicated rather than shared: both files are standalone scripts run as `python3 <abs path>`, where a sibling import resolves through `sys.path[0]` but the same import fails when the module is loaded as `norn.pipelines.*`. Keep the two copies in step.
- `norn/pipelines/_plan_gates_v1.py` and `norn/pipelines/_preplan.py` are private helpers for `plan_with_review_v1`, not pipelines; the catalog skips them by the same `_`-prefix rule. `parse_arg_flags` from `_preplan.py` is also reused by `implement_features_v2` to parse optional `--arg` knobs at import time.
- `plan_with_review_v1` drives codex through `RunCommand`, not an `AgentProvider`, because `Pipeline.agent_provider()` sets one provider for the whole run and `Generate` has no per-stage override — a codex provider would force codex on the drafting stages too.
- Every `Generate` stage in `_plan_review_v1.add_plan_review_stages` sets `CLAUDE_CODE_SUBAGENT_MODEL` to the `standard` label's model, plus `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`. Without that, the Explore and general-purpose subagents a `deep` planning stage spawns run on the deep model too. FORCE is required because the built-in Explore agent declares `model: inherit`, which outranks the plain env var. The split prompt forbids running builds, tests or `test_cmd`s, starting background tasks, and reading outside the repo, because each background build's notification is another full-context round on the deep model.
- `plan_with_review_v1`'s last stage splits the finished plan into `implement_features_v2` step files using the `split-plan` skill (the skill carries v2's contract — the agent never runs git, the run needs a clean tree, a step must change a file unless `allow_noop: true` — because a step written against v1's model, one that commits itself, fails v2's HEAD guard hours in; `StepFilesGate` also rejects front-matter keys v2 refuses to load), resolved through `norn/skills.py` once at import so a worktree run still uses the launch repo's copy. Resolution never raises: it falls back to norn's own `.claude/skills/split-plan/SKILL.md` and then to the bare skill name, because a pipeline that raises at import cannot be loaded at all — the TUI launcher reports `Could not load pipeline` instead of failing the stage. The deliverable is `<slug>-final-plan.md` and the step directory is that path minus `.md` (`tmp/x-final-plan.md` → `tmp/x-final-plan/`); `slug_of` strips only `-preplan`/`_preplan`, so without the `final` marker a brief named `x-plan.md` produced a deliverable called `x-plan-plan.md`.
- A `Loop(on_exhaust=ask_user)` whose body ends in a gate is a **prompt, not a contract**: the runner treats `[c]ontinue` as "proceed" (`norn/runner.py:718-740`), so any mandatory gate must be repeated after the loop as a top-level stage with `on_failure=fail`. `plan_with_review_v1` does this three times (`open questions resolved`, `dispositions recorded`, `step files written`); `implement_features_v2` applies the rule to every loop it has. The post-loop stage must use a **different name** from the in-loop one because `ctx.results` is keyed by stage name. A top-level check that must not abort the run but cannot retry inside a loop exits 0 and writes a marker file; later stages use `when=file_exists(marker)` to gate on the marker's presence.

- `fix_jira_issue_v1` runs `implement_features_v2` as a child subprocess (`sys.executable -m norn run implement_features_v2 <steps_dir> --non-interactive`) rather than importing it directly, because `Pipeline.agent_provider()` sets one provider for the whole parent run and there is no per-stage override; the child process gets its own provider, budget, and checkpoint.
- `--non-interactive` sets `NonInteractiveResponder` as the active responder, which returns abort (`"a"`) on every budget/failure prompt and raises `RuntimeError` on step-mode prompts. Use it only for child processes that must not pause waiting for a human at the terminal. **Every `ask_user` gate in a pipeline is an abort when that pipeline runs as a child**, so a gate whose recoverable answer is knowable in advance must be declarable in the plan rather than left to a prompt — `implement_features_v2`'s step front-matter key `allow_noop: true` is the pattern: a verification-only step declares that it expects to change nothing, and the owned-diff gate passes instead of asking.
- A parent that spawns a child run sees only its exit code, so `fix_jira_issue_v1` follows `implement` with `diagnose implementation` (`when=stage_failed("implement")`, `on_failure=fail`), which runs `norn/pipelines/_child_run.py report` to read the child's own journal (`<launch dir>/<state key>.runs/<n>/`) and end the parent run with the child's failed stage and error. Gates that check the child's artifacts take `when=stage_succeeded("implement")` — without that, `[c]ontinue` at the `implement` prompt walks into a gate that can only report a missing file, several stages removed from the cause. `merge_branch_v1`'s `CiFixChild` (in `_merge_gh.py`) imports `_child_run.py`'s two journal readers directly (`latest_run_dir`, `failed_stage_error`) rather than shelling out to `report` — it needs the failed stage and error text to build its own `ci_fix_failed` halt detail, and `report`'s closing text is written for `fix_jira_issue_v1`, not for a halt.
- **An `ask_user` budget answer extends the budget; it does not wave one stage through.** `runner._check_budget` treats every code in `norn.dsl.BUDGET_EXTENSIONS` (`c` +50%, `d` +100%, `u` no limit) as "raise the limit" and anything else as abort, and `Budget.extend` measures the new limit from what the run has already spent — extending from the old limit would leave a run that overshot still over budget, re-prompting after every remaining stage. `budget_choices()` in `norn/dsl.py` is the ONE home of the codes and labels; `norn/ui.py` and `norn/tui/modals.py` both read it. Limits are also settable per launch, for any pipeline, via `norn run --budget/--token-budget` and the TUI args screen's budget fields, both of which go through `dsl.apply_budget_overrides`. `--budget`/`--token-budget` consume the next token, so they belong in every `_VALUE_FLAGS` copy that scans `sys.argv` for positionals (`_preplan.py`, `_jira_issue.py`, `implement_features_v2.py`).
- The "stage that fails on purpose" pause pattern (`WaitForApproval` in `_plan_review_v1.py`) is a deliberate `StageResult(success=False)` returned by a stage with `on_failure=ask_user`; the runner fires `ASK_USER` and pauses. This is legitimate when the intent is to interrupt the run for a human review step, not to signal an error.
- Switching `implement_features_v2` from its own inline `AssertLaunchTree` to the shared copy in `_launch_tree.py` is deferred until the v1-vs-v2 comparison period ends; do not make that change while v2 is frozen.
- `merge_branch_v1` takes the current feature branch from "committed locally" to "merged into its base branch": resolve the base and rebase, loop the local tests with an LLM fix-or-STOP, push, open/reuse the PR and wait out its checks and Copilot's review (handing red Actions checks to a `check_and_fix_ci_v1` child run), fast-forward merge, and watch the post-merge build. `PROJECT_DIR` is pinned to the launch directory at import time like `check_and_fix_ci_v1`, so the pipeline is NOT worktree-isolated. Nothing it does may enter the target repo — all state lives under a temp work root (`_merge_state.work_root`), never inside the repository, and every `Generate` stage that writes into it passes `add_dirs=[WORK]` (`acceptEdits` only covers the working directory). Lifecycle alerts (`MacOSChannel` on `ASK_USER`/`COMPLETE`/`FAILED`) fire only under `norn run` — the TUI passes no `AlertManager` — and in-run notifications go through `_merge_state.notify`, never a second `osascript` call. Each round is built by `_add_round(n, gate)`: `gate` is `running(PATHS)` for round 1 and `all_of(running(PATHS), file_exists(PATHS.retry(1)))` for round 2, and the two rounds are flat copies, never nested — `dsl.Loop` has no `when`, so a loop nested inside a round would have no way to skip itself once an earlier stage halted. Instead every stage in a round, loop-body stages included, carries the round's own `gate` ANDed onto its own condition, and a loop body whose stages are all skipped (because `gate` is already false) is recorded `success=True` and passes on attempt one at no cost (`runner.py:739-752`). `MAX_ROUNDS = 2`: one round cannot absorb a base that moved between the checks settling and the fast-forward, and a third would mean three CI cycles before a human hears anything. The local-test loop owns its own endings: `check local verdict <n>` is the ONE deliberate retry signal anywhere in the pipeline, `exit 1`ing to re-run the suite after a fix is committed — every other shell gate's `exit 1` means an unpredicted error and becomes an `unexpected_failure` halt. The stop contract is: plain failure (`on_failure=fail`) only before work starts (the four stages up through `resolve branch`) and for the halt/summary machinery itself; a halt for every named condition afterward; `escalate` — the only `ask_user` stage, always last, `when=halted(PATHS)` — pauses the run for a human only when it halted, offering `[a]bort` (recommended; what `--non-interactive` always answers), `[c]ontinue` (ends the run recorded as a success although nothing merged), or `[r]etry` (asks again). `--resume` is refused (`AssertFreshRun`) because a halted guard exits 0 and is checkpointed as a success; recovery is always "fix, then rerun" since every stage is idempotent.
- `norn/pipelines/_merge_state.py` is a private helper for `merge_branch_v1`: the work root and `MergePaths` layout, the halt catalogue (`HALTS`) and `halt`/`halt_shell`, the `HaltOnFailure` mixin and its concrete `HaltingCommand`/`HaltingGenerate`/`HaltingCompressTestLog` subclasses, `HaltOnTimeout`, `CountLocalAttempt`, `AssessLocalFailure`, `AssertFreshRun`, `Escalate`, `WriteMergeState`/`render_summary`, `notify`, and `warn`. `HaltOnFailure` turns an unpredicted failure after `rebase 1` into an `unexpected_failure` halt so a summary always exists once work has started — it is not a warn-and-continue path, since the run still ends failed at `escalate`. It is applied to every stage from `rebase <n>` through `watch base build`, except `count local attempt <n>` (the mixin's own input — it must return a failure unchanged so the loop can retry, not turn it into a halt); it is NEVER applied to the four pre-rebase stages, `ResolveBranch`, the summary writers (`write merge state`, `summarize run`, `finalize merge state`), or `escalate`, since nothing has changed yet before `rebase 1` and the summary/escalation machinery must not itself be swallowed into a halt. `HaltingGenerate` subclasses `Generate` directly (not a wrapper) so the runner's label preflight, which finds stages by `isinstance(impl, Generate)`, still sees it.
- `norn/pipelines/_merge_gh.py` is a private helper for `merge_branch_v1` and the ONE home of every `gh` and remote-git invocation the pipeline makes — `gh`/`git` runners (raising `GhError` on an unexpected exit code), `ResolveBranch`, `rebase_cmd`, the lease-pinned `push_cmd`, `pr_open_or_reuse_cmd`/`pr_not_draft_cmd`/`request_copilot_cmd`, `WaitForChecks` (+ `_poll_until_settled`), `CiFixChild`/`ci_fix_child_cmd`/`sync_after_ci_fix_cmd`, `WaitForCopilotReview`/`FetchPrReviews`, the findings builders, `CheckMergePreconditions`, `merge_cmd`, and `WatchBaseBuild`. Every call except `gh api` is pinned to one repository via `-R $REPO` (`REPO=$(cat <work>/repo)`); `gh api` calls use an explicit `repos/$REPO/...` path instead. The open PR for the branch is reused, never re-created (a mismatched base halts `pr_base_mismatch` rather than silently reusing the wrong one). The Copilot review request is a declared capability probe, not a fallback: a refused `gh pr edit --add-reviewer @copilot` is recorded as `unavailable` (the stage still exits 0) and read back by the later review wait; membership in `COPILOT_LOGINS` and the "already reviewed" check are done with gh's own built-in `-q`, never an external `jq`.
- `ResolveBranch`'s base resolution has four levels, tried in order: `--arg base=` (verified against `origin/<base>`, and it must agree with an already-open PR's base or the run fails before rebasing); the base of an open PR for the branch; the fork-point candidate — `default_branch`, then `main`, `master`, `develop`, `development`, deduplicated against the current branch — with the fewest commits ahead of HEAD (a tie is broken only when every tied candidate shares one merge-base and the default branch is among them; otherwise the run fails asking for `--arg base=`); and finally the repo's default branch when no candidate exists on the remote at all. Before rebasing, it also refuses to overwrite a remote branch that holds commits with no patch-equivalent on HEAD (`git log --cherry-pick --right-only`) — even ones the same human wrote — unless rerun with the one-shot `--arg overwrite_remote=<sha>` pinned to the exact current `origin/<branch>` sha; `RERUN_CMD` (the exact line the summary points a human at) never repeats that flag, so an unattended rerun cannot silently force away commits a second time.
- `WaitForChecks`/`WatchBaseBuild` share one settlement core, `_poll_until_settled`: a check/run set counts as settled only once `is_settled(state)` holds AND the set's stability key (names + states) has stayed unchanged for `SETTLE_WINDOW` seconds of polling — any check appearing or changing mid-poll resets the whole window, not just that one entry — or the wait times out, or the head moves out from under it. `WaitForChecks` additionally waits `HEAD_SYNC_TIMEOUT` for the PR's `headRefOid` to catch up to the pushed sha and grants `NO_CHECKS_GRACE` before treating an empty check set as `checks_none` rather than an instant pass. The same settle-then-re-read pattern repeats at merge time: `check merge preconditions <n>` (`CheckMergePreconditions`) re-reads `gh pr view` right before the push, in a fixed order — `reviewDecision` of `CHANGES_REQUESTED`/`REVIEW_REQUIRED` halts `review_required` first, so an unmergeable PR never burns a round on the checks below; `mergeable == CONFLICTING` or `mergeStateStatus` `DIRTY`/`BEHIND` touches `RETRY-<n>` for round 2 to pick up; a draft halts `pr_draft`; a `headRefOid` other than `green-head` halts `pr_head_moved`, and any drift in the settled check/run set halts `checks_changed`; only then does a non-`CLEAN` `mergeStateStatus` halt `merge_state` — because a check can flip after it first looked green.
- `WaitForChecks` takes `on_red: Literal["fix", "halt"]`. `"halt"` (used by `wait for checks after ci fix {n}`) always halts `checks_red` on a non-green outcome. `"fix"` (used by `wait for checks {n}`) instead hands off to a `check_and_fix_ci_v1` child when every non-green check is in bucket `fail` and its `workflow` maps to exactly one file in `gh workflow list`: it writes `ci-fix-workflows-<n>`, touches `CI-RED-<n>`, and returns without halting — a `cancel` bucket, a failing check with no `workflow` (an external app's status), or a red run with no check of its own still halts `checks_red` even under `"fix"`, since `check_and_fix_ci_v1` only reads GitHub Actions logs. `merge_branch_v1` runs `check_and_fix_ci_v1` as a child (`CiFixChild`) on that hand-off — at most once per round, `--non-interactive`, with the remaining budget passed via `--budget` (never `--arg budget=`, since `check_and_fix_ci_v1` declares no budget of its own): the remainder rule (lowest cost limit minus `ctx.usage_tracker.total_cost_usd`, floored at $1) is `fix_jira_issue_v1.RunChildPipeline.remaining_budget` (`fix_jira_issue_v1.py:250-291`) duplicated on purpose, because that class lives in a pipeline module and cannot be imported. `sync after ci fix {n}` (`sync_after_ci_fix_cmd`) is defense in depth behind `check_and_fix_ci_v1`'s own attribution guard (from step 12) — it halts `attribution_found` only if that guard was somehow bypassed. After a CI fix, Copilot is asked again (`request_copilot_cmd(..., rerequest=True)`) so only a review of the head that actually merges counts; the rerequest path skips the `gh api` reviews query entirely and decides from local state (`copilot-reviewer`, `copilot-requested-head`), and a refusal halts `copilot_rerequest_failed` instead of degrading to `unavailable` — a review is already outstanding by then. `FetchPrReviews` dedupes the three REST sources that together are the complete set of PR feedback (inline review comments — where Copilot's own findings live — are not in `gh pr view --json comments`) against `reviews-seen`, one `<source>:<id>` key per line, never a timestamp: a comment drafted inside a pending review keeps its draft `created_at` until the review is submitted, so an id is the only cursor that agrees across sources.
- `merge_cmd` (`merge pr <n>`) is a plain fast-forward push of the exact commit the checks ran on — `git push origin <green-sha>:refs/heads/<base>` — never `gh pr merge`, `--admin`, `--auto`, or `--force` (locked decision 10): `gh pr merge --squash` discards the individual commits the checks ran against, GitHub's `--rebase` mode re-creates SHAs so the pushed commit is no longer the one that passed CI, and `--auto` returns before the merge happens, ending the run with the outcome unknown. Only `non-fast-forward`/`fetch first` in the push's own output means "the base moved" (`RETRY-<n>`, round 2's job); a bare `rejected` also matches a branch-protection refusal, which halts `merge_rejected` instead. Deviation policy (locked decision 19): a refused fast-forward is never "fixed" with a different merge command; a check that must gate the merge belongs in branch protection, not in this pipeline.
- `_merge_state.warn` is the pipeline's one non-halting report, reserved for `WatchBaseBuild`: when no push-triggered workflow appears on the base within `BASE_RUNS_GRACE` seconds of the merge landing, it writes a `warnings.txt` line instead of halting — the merge already succeeded, so a base with no CI at all is a warning on an otherwise `MERGED` result, not a stop. A red or timed-out post-merge build still halts (`base_build_red`/`base_build_timeout`), and is never handed to `check_and_fix_ci_v1` — fixing the base after the merge already landed is a new change, not this run's job.
- `norn/pipelines/_test_cmd.py` is the one home of `detect_test_cmd`, shared by `check_and_fix_ci_v1` and `merge_branch_v1`; the catalog skips it by the `_`-prefix rule.
- `check_and_fix_ci_v1`'s `--arg workflow=` takes a comma-separated list of workflow filenames (default `ci.yml`), checked in order by `CheckCIWithLogs`, which returns on the first one that isn't green.
- `norn/pipelines/_comment_style.py` is the one home of `COMMENT_RULE`, `ATTRIBUTION_ERE` and `attribution_guard_sh`; every prompt that writes code, commits or PR text in these pipelines appends the rule; the attribution check halts (`merge_branch_v1`) or refuses to commit (`check_and_fix_ci_v1`, from step 12) and never strips.
- `norn/pipelines/_ci_estimate.py` is a private helper for `merge_branch_v1`: per-workflow median CI-run duration (`median_duration`/`workflow_estimate`/`estimate_seconds`, via `_merge_gh.gh`) and `poll_plan` (pre-sleep/interval/timeout for a check wait). It deliberately duplicates the idea in `norn/stages/check_ci.py:684-751` (`_estimate_typical_duration`) rather than sharing it — that core estimator is githubkit-based, single-workflow, falls back to *all branches*, and swallows every error to `None`; sharing it would make `norn/` core depend on the pipeline layer's gh shape. This module instead estimates every workflow a PR runs and takes the max (they run concurrently), falls back to the *base* branch specifically — not all branches (locked decision 7) — when the feature branch has no successful run yet, and lets a `GhError` propagate instead of swallowing it to `None` (AGENTS.md: no fallbacks). `check_ci.py` is untouched.
- `norn/pipelines/_learnings.py` is the ONE home of norn's copy of the Compound Engineering learning schema (enums, `CATEGORY_DEFAULTS`, limits, section lists, `DURABLE_BAR`), the store rules (`resolve_store` reads `docs_root` from `.compound-engineering/config.yaml` only, defaults to `docs/solutions`, raises `StoreConfigError` for a value that leaves the repo, is the repo root, is under `.git/` or escapes through a symlink, and never falls back to `docs`), `keywords_from`, and `validate_learning`. The validator fails closed: every rule is a hard problem line, and the only allowance is a missing cited path marked `removed`/`deleted`/`renamed` on the same line. Learnings are proposals a human commits; nothing norn makes is named `ce-*`. It is also the ONE home of the learn building blocks the pipelines share (`implement_features_v3`, later `check_and_fix_ci_v2`): `LearnPaths` (scratch `learn/` with the agent's only three writable files `learning.md`/`target`/`skipped`, the `learn.ready|skipped|failed|proposed` markers, the `learn.pre.json`/`learn.pre-head` baselines, `outcome.md`), `LearnOutcomeStage` and `LearnGenerate` (decision 5's never-fail contract: an exception, timeout or failed result becomes a recorded outcome; `asyncio.CancelledError` propagates — the runner does not pass a stage its name, so `LearnOutcomeStage` takes `name=`), `learn_prompt`, `decide_learning`, `publish_proposal`, `store_hint` and `outcome_text` (precedence `learn.failed` > `learn.proposed` > `learn.skipped` > none).
- `norn/pipelines/_validate_learning.py` is the human's pre-commit check of a proposal: `<python> _validate_learning.py <doc> --repo <dir> --target <repo-rel> [--base <sha>]`. Exit 0 clean, 1 problems (printed one per line), 2 usage error (argparse, unreadable doc, `StoreConfigError`).
- `norn/pipelines/_find_related.py` is the stdlib-only finder of related learnings, run as `python3 <abs path> <store> <kw>…` like `_step_snapshot.py` (it must not import `norn`) and importable as `find_related`. It ranks by distinct matched keywords over frontmatter fields, keeps the top 25, and adds body matches below 3 hits.
- Stage plugins are discovered from the `norn.stages` entry point group declared in `pyproject.toml`.
- `norn/journal.py` — run journal (events, prompts, outputs persisted per run under `<state-key>.runs/<run_id>/`); `JournalSink` wraps any `EventSink` and writes every redacted event before forwarding it. Journal writes warn-and-continue on I/O failure (the diagnostics-only exception in Principles). `RunJournal.dir` is the public run directory (the learn stages write their `learning.md` proposal there; `runner._write_run_metrics` reads it through the property).
- `norn/metrics.py` — deterministic metrics and rule-based findings computed from the journal at end-of-run (zero tokens); thresholds are module constants. Two rules are not plain constants: `context-bloat` measures the stage's context peak against a fraction of its model's own window (`context_window` in `model_labels.toml`, optional — a label that declares none is skipped), and `stage-timeout` reads `details["timed_out"]` (set by the runner when it cancels a stage) and drops to `info` when a later attempt of the same stage passed; it replaces the generic `agent-error` for that attempt. A killed attempt reports no usage, so its cost is missing from `failed_attempt_cost_usd` and counted in `timed_out_attempts` instead. `compute_metrics` / `find_issues` write `metrics.json` / `findings.json` beside the run journal.
- `norn/compare.py` — `norn compare`: deterministic, zero-token comparison of the last N journaled runs of two state keys from `metrics.json`/`findings.json` (medians, min–max, verdicts `too few runs (need 3)`/`within noise`/`B lower`/`B higher`), and `--bar <digest>` checks of the `## Pass bar` lines a `norn feedback-digest` writes (`met`/`unproven`/`not met`). Core module: no `norn.contrib`/`norn.pipelines` imports. `METRICS`/`is_metric` is the metric vocabulary shared with the digest. A `--group` regex is matched with `re.search` against `stage_name_from_node_id(node_id)` — the bare stage name, never `name` or the node id.
- `norn/evaluate.py` — post-run LLM evaluation: `judge_stage` (haiku, `plan` + `max_turns=1`, no write tools) scores each stage; `run_feedback` (sonnet, `plan` + read-only tools) produces `feedback.md`; `evaluate_run` orchestrates both and writes `evaluation.json`. Evaluation is post-run and journal-driven, not an in-loop quality hook.
- `norn/rating.py` — human rating (1–5): `write_rating` / `load_rating` persist `rating.json` in the run directory; `norn rate` validates the score before any filesystem access.
- `norn/quota.py` — opt-in CodexBar quota sampling and gating; norn never auto-detects CodexBar. Identity fields are stripped before writing. `sample_quota` records usage around a run (activated by `--quota codexbar`); `check_quota_guard` gates the run before it starts via `codexbar guard --min-remaining <pct> --window session|weekly` (activated by `--require-quota <pct>[:window]`, checked in `cli.py` before `run_pipeline`). Guard exit 0 starts the run, 1 blocks it, 64 raises `QuotaProbeError`, and 69 (quota unavailable — also a missing binary or a timeout) blocks unless `--quota-fail-open`. A bare `--require-quota` skips the guard and only aborts on probe failure. `--quota-fail-open` overrides `--require-quota` in both places, so `run_pipeline(require_quota=...)` is already the resolved boolean.
- `norn/transcripts.py` — opt-in claude-code transcript reader; reads the local transcript for per-turn model-mix data. A missing transcript file is recorded as `"missing"`, not raised (the file exists only after a run that used claude-code).
- `StageResult.details` — free-form dict attached by stages that want to persist structured data beyond the plain `output`; serialised by the run journal (`norn/journal.py`); not stored in the checkpoint and not forwarded to `StageLogEntry`.
- The `plan` permission mode + `max_turns=1` no-write-tools idiom is now used in norn core (`norn/evaluate.py`) for LLM judging: the agent sees the journal but cannot modify files, so the judge is a pure reader.
- Evaluation cost is tracked separately in `evaluate_run` (not added to `UsageTracker`, `.history`, or any pipeline budget) and reported after the run.
- `norn/model_labels.toml` is the ONE home for every model id and reasoning effort; `norn/model_labels.py` loads and validates it. A guard test in `tests/test_model_labels.py` scans `norn/**/*.py`, `bin/`, and `examples/` and fails if any file outside the loader contains a raw model id or the transitional shorthands `haiku`/`sonnet`/`opus`.
- **Effort is mandatory and explicit.** Every `claude-code` call sends `--effort <value>` and every `codex` call sends `-c model_reasoning_effort=<value>`, both derived from the label. `opencode` forbids effort (no `--variant` verified). `CLAUDE_CODE_EFFORT_LEVEL` in any env source is rejected — effort comes from the label, not from env.
- Codex is not an `AgentProvider`; pipelines that use codex (`plan_with_review_v1`, `_plan_review_v1.py`) drive it through `RunCommand` and always pass `-m <model>` and `-c model_reasoning_effort=<effort>` resolved from the label. There is no codex provider path.
- `implement_features_v2` rejects `effort:` in step front-matter; the label is the tuning unit. `implement_features_v1.py` (v1) is frozen except for the one permitted post-freeze edit: the `--root` filter in `_snapshot_diff.py` that prevents a single gitignored path from aborting the commit stage.
- `run_pipeline` preflights every `Generate` stage's label before the first stage runs. A missing label combined with a missing `default_model` is a hard error that surfaces before any agent token is spent.

## UI And Event Seam
- The terminal UI (`norn ui`), the typed run-event seam (`norn/events.py`, `norn/event_sink.py`), and the Textual code under `norn/tui/` are documented in `docs/norn-ui.md`; read it before touching any of them.
- `docs/norn-ui.md` is canonical and MUST be updated in the same change whenever you alter `norn/tui/`, the event seam, the runner's event emission, the launcher/args/run flow, or the `norn ui` CLI wiring.
- Textual is a REQUIRED dependency, declared in `[project.dependencies]`; there is no optional `ui` extra. Per Principles, `norn ui` imports `norn.tui` directly and a missing Textual fails hard — no `ImportError` guard, no install hint, no degraded path. The same applies to `fzf` (the file picker raises loudly when it is not installed).
- Keep all `textual` imports inside `norn/tui/` and import them lazily from the `ui` command so `norn run`/`norn history`/etc. stay light — this is import locality (don't load Textual unless `norn ui` runs), NOT optionality. Textual is always installed.

## Stage Semantics
- All stage `run()` methods are async and return `StageResult`; leave `name=""` in custom stages because the runner sets the real stage name.
- Set `needs_agent = True` only for stages that need agent provider kwargs; non-agent stages must not import `claude-agent-sdk`.
- A `Loop` retries the whole body from the top after any failing stage, not just the failed stage.
- `clear_context()` drops only the current agent session; prior `StageResult` outputs remain available through `ctx.get("stage name")`.
- `Parallel` runs stages concurrently and each agent-backed stage starts with a fresh session.
- Relative paths in stage `run()` methods resolve against `ctx.working_dir` via `resolve_run_path` (in `norn/runner.py`) when set; absolute paths pass through unchanged. This is the durable worktree-isolation contract — stages must use `resolve_run_path` rather than bare `pathlib.Path` for any filesystem access.
- Contrib stages are not worktree-aware in v1: `norn/contrib/` stages (`ci.py`, `ship.py`, `push.py`) shell out relative to process cwd or `IssueContext.local_path` (the `Clone` stage owns its own checkout), and the `implement_features_v1` and `check_and_fix_ci_v1` pipelines pin `PROJECT_DIR = os.getcwd()` at import time for their `RunCommand` `cd` and git calls. These run against the launch repo even under the worktree toggle. Their `Generate` stages deliberately do NOT set `cwd=`, so agent work follows `ctx.working_dir`.

## Agent Provider
- Default provider is `claude-code` (Claude Agent SDK). `opencode` is also supported via the OpenCode CLI.
- Select provider via `--agent-provider` CLI flag, `NORN_AGENT_PROVIDER` env var, or `Pipeline.agent_provider(...)` (priority in that order).
- Checkpoint and history records store `agent_provider`; `--resume`/`--continue` with a mismatched provider exits with an error.
- Hooks, MCP tools, and non-`project` `setting_sources` are `claude-code`-only and fail fast with other providers.
- `AgentUsage` is the usage of ONE call, whatever the provider reports. The Claude Code CLI reports tokens, turns and `duration_ms` per round, and one call has several rounds when a background task or subagent finishing wakes the agent again; `ClaudeCodeProvider` adds the rounds up. `total_cost_usd` and `duration_api_ms` are running totals for the whole session, carried over by `--resume` and copied by `--fork-session`, so the provider charges a call the latest total minus what the resumed session had already reached. `norn/agents/session_totals.py` is that process-wide ledger, keyed by session id. The checkpoint saves the checkpointed session's totals, and `--resume` (runner) and `--continue` (cli) seed them back, so the first stage resuming in a new process is not charged the session's whole history. Subagent tokens are missing from the per-call token counts because the SDK drops the CLI's `modelUsage`, but their cost is in the session total.

## Generate Stage Quirks
- If `permission_mode` or `allowed_tools` is set, the agent writes files through tools and `Generate.output_file` is ignored.
- Use absolute paths in prompts for agent-backed file edits; bundled pipelines do this because the bundled CLI may resolve its project root differently.
- Use `setting_sources=["project"]` when a Generate stage should load repo guidance such as `AGENTS.md` or `CLAUDE.md`.
- `Generate(model=...)`, `Pipeline(default_model=...)`, every `--arg *model*` knob, and step front-matter `model:` take a **label** from `norn/model_labels.toml` (`light`, `standard`, `deep`; `review` for codex). Raw model ids are rejected. `norn models` prints the current mapping.

## Config And Secrets
- The CLI loads env files automatically in this order: `~/.norn/env`, then `.norn.env`; explicit process env vars win.
- Real Generate stages need Claude auth via `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`.
- Org configs are Python pipeline files under `~/.norn/orgs/` or `NORN_CONFIG_DIR/orgs/`; issue-key runs choose an org by matching `Pipeline.projects(...)` keys.
- Treat local agent settings such as `.claude/settings.local.json` as user-local and potentially secret; do not copy their values into docs, tests, or commits.

## Tests
- Unit tests mock SDK calls, subprocesses, GitHub/Jira/search, and other external systems; keep new tests offline unless explicitly writing an E2E/BATS test.
- Use `pytest.mark.asyncio` for async tests even though `asyncio_mode = "auto"` is configured.
- BATS test fixtures live under `bats/testfiles/`; generated runtime files should go under `tmp/` or `target/`, both ignored.
